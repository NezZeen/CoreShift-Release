# Аудит безопасности CoreShift, октябрь 2026

Версия: 0.7.1 (`49ba95b`). Что проверялось: движок (`engine/`), интерфейс (`app/`) и сборка (`packaging/`) на Windows, Linux и Android.

Модель угроз:

- непривилегированный пользователь или вредоносная программа на том же компьютере;
- другое приложение на том же телефоне;
- вредоносная или взломанная подписка либо панель;
- сетевой атакующий: подмена обновлений, DNS;
- вредоносная веб-страница в браузере пользователя: DNS rebinding, CSRF к локальному API;
- оператор VPN-сервера (в ограниченной мере).

Что защищается: ссылка подписки, токен локального API, целостность обновлений, трафик и DNS пользователя, права SYSTEM/root у службы.

Исправления 0.6.8 (учётные данные SOCKS, ACL `SecureDataDir`, проверки DNS-журнала, поэтапный запуск установщика, подписанные манифесты) перепроверены и работают, как задумано.

## Исправлено

### H1. Ядро, не открывшее свой SOCKS-порт, считалось работающим (высокая)

Где: `engine/internal/supervisor/supervisor.go` (`launch`, `awaitHealthy`, `monitor`), `engine/internal/supervisor/process.go`.

Супервизор считал ядро запущенным, как только порт `127.0.0.1:17890` начинал принимать соединения. Если порт в этот момент держит другая программа, Xray и sing-box завершаются с ошибкой bind. Mihomo же пишет `listen err: … bind` и продолжает работать без своего входа. Это проверено на mihomo 1.19.31. Тогда порт отвечает, но за ним не ядро, а чужая программа, и TUN-слой отправляет туда трафик устройства.

Сценарий: другое приложение на телефоне или другой пользователь компьютера занимает порт, пока ядро перезапускается. Супервизор принимает ядро за рабочее, и трафик всех приложений в VPN уходит этому процессу.

Исправление. Вывод ядра проверяется на его собственную ошибку `listen tcp <адрес>: bind`:

- ошибка при запуске — запуск считается неудачным, супервизор переходит к следующему ядру;
- ошибка у уже работающего ядра — оно сразу заменяется, проверки здоровья не ждут.

Работает одинаково на Windows, Linux и Android. Тесты: `porttaken_test.go`, у fakecore появились режимы `port-taken` и `port-taken-after`.

### M1. Папка программы на Windows (средняя)

Где: `packaging/windows/coreshift.iss`, `LockDownAppDir` и `PrepareToInstall`.

Установщик разрешает выбрать любую пустую папку. Права у неё он менял, а владельца — нет. Если пустую папку заранее создал обычный пользователь (вне Program Files, например `D:\Apps\CoreShift`), она оставалась за ним. Владелец всегда может вернуть себе запись и подменить файлы службы, которая работает от SYSTEM. Кроме того, при обновлении `UnlockAppDir` сбрасывал права папки к правам родителя (на `C:\` это запись для «Прошедших проверку»), пока копировались новые файлы.

Исправление: папка и всё в ней передаются Администраторам (`icacls /setowner *S-1-5-32-544 /T`) и закрываются от пользователей до копирования файлов и ещё раз после. Права файлов 0.4.0-бет восстанавливаются тем же шагом. Скрипт собирается ISCC.

### M2. Журнал, копируемый для поддержки (средняя)

Где: `app/lib/state/app_state/actions.dart` (`journalForSupport`), новый `app/lib/state/redact.dart`.

Пользователь вставляет журнал в чаты (Telegram). Ядра и TUN-слой печатают, куда шли неудачные соединения (`to www.site.example:443`), адрес сервера, иногда ссылки и UUID VLESS/VMess. Около сбоя в копию попадает весь вывод ядер, без фильтра по уровню.

Исправление. В копии:

- у ссылок остаётся только схема (`https://…`);
- UUID заменяются на `<uuid>`.

Сайты и внешние IP-адреса в копии остаются: по решению владельца проекта они нужны для разбора сбоев (какой сервер не отвечает, какой сайт не открылся). Сначала они тоже скрывались (`<домен>`, `203.0.x.x`), это вернули. На странице журнала строки не меняются. Тест: `app/test/redact_test.dart`.

### M3. На Windows токен API мог прочитать любой локальный пользователь (средняя)

Где: `engine/internal/service/secure_windows.go` (`WriteShared`, `KeepShared`), новый `engine/internal/service/apigroup_windows.go`, `engine/cmd/coreshiftd/winservice_windows.go` (`service install`, `service remove-group`, запуск службы), `packaging/windows/coreshift.iss`, `app/lib/platform/api_access.dart`, `app/lib/ui/shell.dart`.

`api.json` читали все локальные пользователи (`BU`), значит, любой из них управлял службой:

- `GET /v1/subscriptions/{id}/url` отдаёт полную ссылку подписки с токеном;
- можно добавить свою подписку или DNS-сервер и подключить VPN, после чего трафик всех пользователей машины пойдёт через чужой сервер.

Повысить права до SYSTEM через API нельзя: пути, бинарники и источники обновлений проверяются (см. «Проверено»).

Исправление — как на Linux, локальная группа «CoreShift Users»:

- DACL `api.json`: SYSTEM и Администраторы — полный доступ, группа — чтение. Пользователи (`BU`), интерактивные (`IU`), прошедшие проверку (`AU`) и «Все» доступа не имеют. Нет группы — файл читают только SYSTEM и Администраторы. Каталог данных, как и раньше, можно только просмотреть: так приложение отличает остановленную службу от запрета.
- Группа попадает в токен пользователя только при входе в систему. Поэтому служба вписывает в DACL ещё и каждого участника группы по его SID и перечитывает состав группы раз в 15 секунд (`KeepShared`). Добавленный участник получает доступ без выхода из системы и без перезапуска службы, приложение подключается само. Удалённый теряет доступ так же.
- `coreshiftd service install` (его запускает установщик) создаёт группу и добавляет пользователя, вошедшего в сеанс установщика (WTS). Это тот, кто запустил установку, даже если права дал пароль администратора. Поэтому приложение, запущенное сразу после установки, работает.
- Обновление со старой версии. Если группы ещё не было, в неё попадают и пользователи, чьё приложение прервало самообновление (`updates/pending.json`). Самообновление идёт от SYSTEM в сеансе 0, где никто не вошёл. Если таких пользователей нет — пользователь консоли. Ручное обновление добавляет того, кто его запустил. Следующие обновления состав группы не трогают: удалённый администратором участник не вернётся.
- Служба при запуске создаёт группу, если её нет.
- Удаление CoreShift удаляет группу (`coreshiftd service remove-group`). `service uninstall` её не трогает: установщик обновления тоже удаляет старую службу.
- Приложение: если Windows отказал в чтении `api.json`, показывается экран «Нет доступа к службе» с командой для администратора — `net localgroup "CoreShift Users" "<учётная запись>" /add`. Кнопки «Запустить службу» нет, и приложение не перезапускает службу.

Администратор без повышения прав тоже не читает файл без группы: UAC убирает группу Администраторов из его токена. Установщик добавляет его как любого другого.

Тесты: `apigroup_windows_test.go` (SDDL без `BU`/`IU`/`AU`/`WD`; участник по SID читает файл, посторонний получает отказ; состав группы; пользователь сеанса; `pending.json`), `app/test/api_access_test.dart`. Скрипт установщика собирается ISCC.

### L1. Постоянный порт API 17900 (низкая)

Где: `engine/cmd/coreshiftd/vpn.go` (`serveWith`, `openAPI`), `engine/internal/service/api.go` (`APIProof`, `GET /v1/hello`), `app/lib/platform/platform_io.dart` (`HttpBackend`), новый `app/lib/api/proof.dart`.

Если порт был занят до старта службы, служба не запускалась. Если служба падала и оставляла `api.json`, приложение обращалось к тому, кто занял порт, и могло отправить ему ссылку новой подписки.

Исправление:

- Служба слушает порт, который выбирает система (`127.0.0.1:0`), и записывает его в `api.json`. Занять его заранее нельзя. Флаг `-api` остался.
- `api.json` прошлого запуска удаляется первым делом при старте.
- Служба доказывает, что знает токен. На запрос с заголовком `X-CoreShift-Nonce` она отвечает заголовком `X-CoreShift-Proof`: HMAC-SHA256 от `coreshift-api-proof`, нулевого байта и nonce с токеном в качестве ключа. Доказательство выдаётся только после проверки токена и `Host`, сами проверки не изменились.
- Приложение, прочитав `api.json`, сначала спрашивает `GET /v1/hello` со случайным nonce и проверяет ответ. Только потом идут остальные запросы. Доказательство проверяется и в каждом ответе, и у потока событий. Если ответил не тот, кто записал файл, приложение пишет «По адресу из файла службы отвечает другая программа…» и больше туда ничего не отправляет. SHA-256 и HMAC написаны на Dart без новых пакетов и сверены с векторами FIPS 180-4, RFC 4231 и с Go.
- Linux: то же самое. Права `api.json` прежние: `root:coreshift 0640` в каталоге `0710`.
- Android: движок работает в процессе приложения и уже брал случайный порт. `api.json` лежит в личной папке приложения (0600) и перезаписывается при каждом запуске, а упасть движок может только вместе с приложением. Отдельных изменений не понадобилось, проверка доказательства работает и там.

Тесты: `cmd/coreshiftd/api_test.go` (порт 0, старый файл заменяется), `TestAPIProvesItKnowsTheToken`, `app/test/api_proof_test.dart` (подставной сервер на порту из устаревшего `api.json` не получает ни тела запроса, ни потока событий).

### L2. Таймауты HTTP-сервера API (низкая)

Где: `engine/internal/service/api.go` (`NewAPIServer`, `apiLimits`, `bodyLimit`, `streams`), `engine/cmd/coreshiftd/vpn.go`, `engine/mobile/engine.go`.

Был задан только `ReadHeaderTimeout`, а число подписчиков `/v1/events` не ограничивалось. Угроза — локальный отказ в обслуживании, и только у владельца токена.

Исправление (Windows, Linux и Android, общий `NewAPIServer`):

- `ReadHeaderTimeout` 10 с, `ReadTimeout` 30 с, `IdleTimeout` 2 мин, `MaxHeaderBytes` 64 КиБ.
- Поток `/v1/events` снимает с себя таймаут чтения (`ResponseController.SetReadDeadline`). Читатель потока, который перестал читать, отключается через 30 с на записи.
- Тело запроса — до 64 КиБ. У `POST /v1/connect`, `POST /v1/subscription/parse`, `POST /v1/subscriptions`, `PATCH /v1/subscriptions/{id}` и `PUT /v1/settings` — до 1 МиБ. Больше — ответ 413.
- Одновременно открыто не больше 16 потоков событий. Новый поток сверх предела закрывает самый старый, а не получает отказ. Так приложение, переподключившись, не упрётся в свой же зависший поток, который служба заметила бы только на следующем ping.

Тесты: `engine/internal/service/api_limits_test.go`: незаконченные заголовки, тело, которое не приходит, простаивающее соединение, слишком большие заголовки (431), поток событий живёт дольше `ReadTimeout`, 17-й поток закрывает первый, лимиты тела (413).

### M5. Порт SOCKS освобождался при смене ядра (средняя)

Где: новый `engine/internal/socksgate/gate.go`, `engine/internal/supervisor/supervisor.go` (`Connect`, `serve`, `launch`, `coreListens`), `engine/internal/supervisor/latency.go`, новый `engine/internal/proc/owner*.go`.

Каждое ядро само открывало порт `127.0.0.1:17890`. При смене или перезапуске ядра порт был свободен, пока новое ядро не откроет его. В журнале это видно как `outbound/socks[proxy]: dial tcp 127.0.0.1:17890: connect: connection refused`. В этот миг порт могло занять любое приложение с разрешением INTERNET на телефоне или другой пользователь компьютера. Соединения, начатые в это время, ушли бы к нему, а вместе с ними и учётные данные SOCKS.

Исправление:

- Порт 17890 держит сам движок от подключения до отключения (`socksgate`). Он проверяет учётные данные клиента (без TUN порт, как и раньше, открыт для программ пользователя), подключается к текущему ядру и дальше передаёт байты без изменений, так что любые команды SOCKS работают так, как их делает ядро. Смена ядра порт не закрывает. Соединения, пришедшие во время смены, ждут новое ядро до 10 секунд, а не получают отказ.
- Каждое ядро слушает свой случайный порт на loopback, и при каждом запуске у него новые логин и пароль. Их знает только движок: ни TUN-слой, ни программы пользователя их не получают. Так же запускаются пробные ядра и замеры задержки; запасного порта 17891 больше нет.
- Случайный порт ядра свободен миг между выбором и открытием. Поэтому движок принимает ядро, только если система подтверждает, что порт слушает именно процесс ядра: на Windows — по таблице `GetExtendedTcpTable` (PID владельца), на Linux — по inode сокета из `/proc/net/tcp` среди открытых файлов ядра. Чужая программа на порту — запуск неудачный, ядро пробуется на другом порту. Android 10+ не даёт приложениям читать таблицы сокетов; там остаётся случайный порт и пароль ядра.
- На Windows порт движка открыт с `SO_EXCLUSIVEADDRUSE`: другой сокет не сядет на него и с `SO_REUSEADDR`. На Linux и Android это и так запрещено без `SO_REUSEPORT` у обоих сокетов.

Тесты: `engine/internal/socksgate/gate_test.go` (учётные данные, открытый порт без TUN, UDP ASSOCIATE через sing, смена ядра, ожидание ядра, порт не занять ни простым `listen`, ни с `SO_REUSEADDR`/`SO_REUSEPORT` через 20 смен), `engine/internal/supervisor/gate_test.go` (порт не освобождается, пока ядра падают одно за другим; соединение во время смены доходит до следующего ядра; у порта ядра свои учётные данные), `TestImpostorOnTheCorePortIsRefused` (чужой процесс на порту ядра, принимающий любой пароль, не получает трафика), `engine/internal/proc/owner_test.go`, `TestLiveSOCKSPort` и `TestLiveTakeoverDuringSwap` с настоящими xray 26.3.27, sing-box 1.14.2 и mihomo 1.19.31 (TCP и UDP). Тесты пакетов проходят на Windows и в WSL (Linux).

### M6. IPv6 мимо туннеля при выключенном IPv6 (средняя/низкая)

Где: `engine/internal/service/connect.go:333`, `store/settings.go` (`IPv6`).

С выключенной настройкой «IPv6» TUN поднимается только с IPv4.

- Android сам блокирует семейство без маршрута.
- На Linux `strict_route` делает IPv6 недоступным.
- На Windows IPv6-трафик с собственным IPv6 хоста идёт мимо туннеля. Через DNS AAAA-записи не приходят, но они приходят через встроенный DoH браузера, WebRTC и адреса, записанные в программах. Тогда виден реальный IPv6-адрес.

По умолчанию IPv6 включён.

Уточнение при исправлении: по коду sing-tun (`tun_windows.go`) при `strict_route` и TUN без IPv6-адреса на Windows ставится WFP-фильтр, который запрещает весь исходящий IPv6, кроме самого sing-box. Тогда IPv6 не утекал бы, но не работали бы и `::1`, и IPv6 локальной сети. На реальной машине это не проверялось, а поведение зависело бы от версии sing-box.

Исправление (`engine/internal/tunlayer/tunlayer.go`, `Options.RefuseIPv6`; `engine/internal/service/connect.go`). Одно правило для Windows и Linux:

- С выключенной настройкой TUN всё равно получает IPv6-адрес (`fdfe:dcba:9876::1/126`) и маршрут `::/0`. Диапазоны локальной сети (`fe80::/10`, `fd00::/8`, мультикаст) в него не входят, `::1` тоже.
- sing-box отклоняет IPv6 (`reject`, `no_drop`) первым правилом, до `sniff`. Так правило срабатывает до установления соединения (PreMatch): TCP получает RST вместо рукопожатия, UDP — ICMP unreachable. Программы сразу переходят на IPv4, не дожидаясь таймаута.
- DNS по IPv6 (Windows спрашивает и IPv6-резолвер TUN) по-прежнему перехватывается. DNS отвечает только A-записями (`ipv4_only`), проверки IPv6 Windows получают пустой ответ.
- Android не меняется: VpnService сам блокирует IPv6, если у TUN нет IPv6-адреса.
- Если система не даёт интерфейсу IPv6 (Linux: `disable_ipv6`; Windows: `DisabledComponents` с битом `0x10`, новый `service/ipv6_windows.go`), TUN остаётся только с IPv4, а IPv6 закрывает `strict_route`. Если адрес всё же не встал, служба перезапускает TUN только с IPv4 и пишет об этом в журнал.
- Описание настройки в приложении теперь говорит, что выключенный IPv6 не работает вовсе, а не идёт мимо VPN.

Проверка:

- `TestRefuseIPv6`, `TestRefuseIPv6Platform` (tunlayer), `TestIPv6Tunnel`, `TestIPv6RefusedFallsBackToIPv4Only`, `TestIPv6DisabledBy` (service);
- `sing-box check` 1.14.2 для новых вариантов конфига;
- `TestRefuseIPv6Live` поднимает настоящий TUN в отдельных netns WSL (`tunlayer/testdata/refuse-ipv6-netns.sh`). 60 TCP-подключений к внешнему IPv6 отклонены, самое долгое — 14 мс. UDP получает «connection refused» за 0,2 мс. IPv6-узел локальной сети доступен, DNS по IPv6 отвечает. С правилом после `sniff` тот же тест показывает установленное соединение.

На Windows TUN не поднимался (на машине работает VPN пользователя): нужна проверка на реальном устройстве с IPv6 у провайдера, например test-ipv6.com при выключенной настройке.

### L4. Ужесточение systemd (исправлено)

Исправление (`packaging/linux/coreshift.service`, описание в `packaging/linux/README.md`, раздел «Ограничения службы»). `systemd-analyze security coreshift`: было 6.7 MEDIUM, стало 3.2 OK. Ядра, TUN-слой и программы DNS работают в той же песочнице, что и служба.

- Capabilities: убраны `CAP_DAC_OVERRIDE`, `CAP_KILL`, `CAP_NET_BIND_SERVICE`. Остались `NET_ADMIN`, `NET_RAW`, `SYS_PTRACE` и `DAC_READ_SEARCH` (правила по приложениям), `CHOWN` и `FOWNER` (`SecureDataDir`).
- `ProtectSystem=strict`. Запись разрешена только в `/var/lib/coreshift`, каталог ядер, `/etc` (`resolv.conf` заменяется атомарно), `/run/resolvconf`, `/run/netconfig`, `/var/adm/netconfig` и `/proc/sys/net/ipv4/conf` (`rp_filter` интерфейса TUN). Удалённый пользователем `/var/lib/coreshift` юнит создаёт заново (`ExecStartPre=+mkdir`).
- Добавлены `DevicePolicy=closed` (только `/dev/net/tun`), `ProtectKernelTunables`, `ProtectKernelLogs`, `ProtectClock`, `ProtectHostname`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK`, `RestrictNamespaces`, `MemoryDenyWriteExecute`, `SystemCallArchitectures=native`, `SystemCallFilter=@system-service`.
- Проверено в WSL. На Ubuntu 24.04 с собранным пакетом: подключение с каждым ядром через TUN, DNS, откат после `kill -9`, обновление пакета. `dns apply`/`revert` в той же песочнице: Ubuntu (resolved, файл), Fedora 44 (файл, resolved, firewalld, NetworkManager), openSUSE Tumbleweed (netconfig, файл), Debian 13 и Arch (файл).

### L5. Android: перенос между устройствами (исправлено)

`app/android/app/src/main/AndroidManifest.xml`: на Android 12+ `allowBackup="false"` не запрещает перенос данных на новое устройство. Ссылки подписок с токенами и настройки могли уйти на новый телефон.

Исправление:

- `android:dataExtractionRules="@xml/data_extraction_rules"` (Android 12+) исключает все области данных (`root`, `file`, `database`, `sharedpref`, `external` и их `device_*`) и из облачной копии, и из переноса между устройствами;
- `android:fullBackupContent="@xml/backup_rules"` (Android 11 и старше) исключает то же самое на случай, если резервное копирование там включат вопреки `allowBackup="false"`;
- `allowBackup="false"` остался.

Подписку на новом телефоне нужно добавить заново. Атрибуты есть в манифесте собранного APK (`aapt2 dump xmltree`).

### L6. Наборы правил (исправлено)

`engine/internal/service/rulesets.go`: `.srs` скачивались с `raw.githubusercontent.com/SagerNet` по HTTPS, а проверялось только начало файла (`SRS`). Подменённый набор мог отправить выбранные сайты мимо туннеля, например добавить в `geoip-ru` сеть `0.0.0.0/1` или 8.8.8.8, или заблокировать их. Хеш в коде не годится: SagerNet обновляет базы каждые несколько дней.

Что выбрано:

- **Встроенные копии.** Базы лежат в `engine/internal/ruleset/data` и встраиваются в службу (`go:embed`), одинаково на Windows, Linux и Android. Им можно доверять настолько же, насколько выпуску: самообновление ставит только подписанное. Служба начинает с них, если на диске базы нет, она испорчена или старше встроенной. Подключение больше не ждёт загрузки.
- **Проверка скачанного** (`ruleset.Check`). Свежая копия скачивается сама, раз в неделю, сначала через туннель. Она заменяет прежнюю, только если:
  - читается как база sing-box, а распакованная не больше 64 МБ;
  - состоит из одних имён или одних адресов: без логических и инвертированных правил, портов, процессов;
  - содержит то, для чего нужна: google.com и youtube.com в `geosite-google`, адреса Яндекса в `geoip-ru`, yandex.ru и vk.com в `geosite-category-ru`, meduza.io в `geosite-category-media-ru-blocked`;
  - не содержит контрольных имён и адресов: в списке «напрямую» нет meduza.io, telegram.org, github.com и подобных, в `geoip-ru` — 8.8.8.8, 1.1.1.1, серверов Google и GitHub, сетей шире /8 и больше 134 млн IPv4-адресов; ни одна база не совпадает со случайными именами;
  - по числу записей и охвату адресов не меньше половины и не больше примерно двух прежних копий — и той, что на диске, и встроенной;
  - не добавляет записей на целые зоны (ключевые слова, регулярные выражения, домены верхнего уровня), которых нет ни в одной из прежних копий.

  Иначе остаётся прежняя копия, и в журнале появляется «база … не обновилась, работает прежняя». Предупреждения «пойдут через туннель» при этом нет.
- **Выпуск.** `release.ps1` перед коммитом версии обновляет встроенные копии командой `coreshift-release rulesets` и проверяет их по прежним. Если база сильно изменилась, выпуск останавливается до коммита и тега; принять её можно флагом `-accept` после проверки вручную. Описание — в `packaging/README.md`, раздел «Базы правил».

Почему не подписанный манифест с хешами баз. Ключ подписи есть только на компьютере разработчика, поэтому подписанные базы обновлялись бы не чаще выпусков. Встроенные копии дают то же доверие без лишнего манифеста и загрузки. Свежесть между выпусками дают проверенные загрузки.

Тесты: `engine/internal/ruleset/ruleset_test.go` (встроенные копии читаются и сходятся с `sets.json`; отклоняются страница ошибки, обрезанный и испорченный файл, урезанный `geoip-ru`, `geoip-ru` с 8.8.8.8 или `128.0.0.0/1`, Google без google.com, российский список с meduza.io, `.com`, `.*`, новым ключевым словом или доменом верхнего уровня, логические, инвертированные правила и правила с портами; обычное обновление принимается), `engine/internal/service/rulesets_test.go` (отклонённая копия оставляет прежнюю на диске, принятая заменяет её; испорченная или устаревшая база на диске заменяется встроенной), `engine/cmd/coreshift-release/rulesets_test.go`.

## Проверено, замечаний нет

### Локальное API

- Токен (32 случайных байта) сравнивается за постоянное время.
- `Host` проверяется по адресу и порту слушателя: DNS rebinding закрыт.
- CORS-заголовков нет, а Bearer-заголовок требует preflight: CSRF закрыт.
- Тело запроса ограничено: 64 КиБ, у подписок, ссылок и настроек 1 МиБ (L2).
- Ни один эндпоинт не принимает путей к файлам, бинарникам или конфигам ядер. Источник обновлений — `github:`/`github-public:` или локальная папка (не UNC), и её содержимое всё равно проверяется подписью.

### Подписки

- Все форматы разбираются в фиксированную модель `node.Node`. `external-controller`, `log`, `rule-providers`, `tun`, скрипты и прочее из подписки не переносятся.
- Конфиги ядер строятся через `json`/`yaml.Marshal`: внедрить ключи через значения нельзя.
- `xhttp extra` и опции SIP003 проверяются по белому списку и при разборе, и при рендере. Сюда относятся и узлы из `/v1/connect {"node": …}`.
- Тело подписки ограничено 16 МБ, узлов не больше 5000.
- YAML alias-бомба отклоняется (новый тест `subscription/bomb_test.go`).
- Ошибки разбора не содержат ссылок и учётных данных.

### Самообновление

- Манифест проверяется подписью Ed25519, установщик — SHA-256 и размером.
- `Newer` не даёт откатить версию; тип установщика зависит от платформы.
- На Windows установщик запускается из закрытой копии, удерживаемой открытой.
- Android APK дополнительно проверяет система (тот же ключ).
- На Linux обновление только объявляется, страница релиза проверяется.

### Файлы

- `C:\ProgramData\CoreShift` закрыта для пользователей и забирается у чужих владельцев.
- `/var/lib/coreshift` — 0710 root:coreshift, `api.json` — 0640, остальное — 0600/0700.
- Конфиги ядер с учётными данными записываются в закрытые каталоги.

### Ядра

- SOCKS-входы, в том числе в тестах задержки, требуют случайные учётные данные.
- Clash API sing-box и mihomo защищены секретом.
- У Xray включён только StatsService, журнал доступа выключен.
- Всё слушает только на loopback.

### Windows

- Путь службы экранирован (`mgr.CreateService`).
- SDDL службы даёт пользователям только запуск.
- `coreshift://` открывается как `"coreshift.exe" "%1"`.
- Ссылки панелей открываются только по схемам http(s), tg и mailto.

### Android

- VpnService защищён `BIND_VPN_SERVICE`.
- Плитка защищена `BIND_QUICK_SETTINGS_TILE`.
- `BootReceiver` проверяет action (защищённая рассылка).
- `InstallStatusReceiver` не экспортирован.
- `taskAffinity=""`, `allowBackup="false"`.
- API на случайном порту, токен в приватном каталоге.

### Ссылки импорта

`coreshift://` (система открывает CoreShift только по этой схеме), ссылки других клиентов из буфера обмена и QR ничего не добавляют без подтверждения в диалоге.

### Утечки

- DNS перехватывается (`hijack-dns`), локальные резолверы тоже.
- NRPT/resolved меняются с журналом отката.
- Когда все ядра отказали или TUN-слой упал, служба снимает TUN и возвращает DNS.
- Android блокирует IPv6 без маршрута; Windows и Linux с выключенным IPv6 забирают его в TUN и сразу отклоняют (M6).
